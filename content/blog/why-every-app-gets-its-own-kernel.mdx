## The shared-kernel problem

A container is a set of Linux namespaces and cgroups. Every process inside still talks to the same kernel as the host. A kernel bug reachable from inside one app is a way out of all of them.

For a homelab that's not theoretical. You run images pulled from the internet, often as root, next to the disks that hold everything you care about. We wanted the convenience of containers with the boundary of a VM.

<Callout tint="yellow" className="text-body-s">
  **Short version:** apps in Crustates get their own kernel by default. You still deploy container
  images and Compose files; you just don't share a kernel with them.
</Callout>

## What a microVM is

A microVM is a virtual machine with almost everything removed: no BIOS, no emulated legacy devices, a minimal kernel and virtio for disk and network. It boots in well under a second and uses tens of megabytes of memory on top of the app itself.

## Kata runtime-rs on Cloud Hypervisor

We didn't write our own VMM. containerd hands each app to the Kata Containers shim, which since Kata 4.0 is written in Rust (runtime-rs). The shim starts a Cloud Hypervisor microVM, mounts the image and runs the container inside it. To containerd it looks like any other runtime.

## When to opt out

Some boards can't run Cloud Hypervisor microVMs (the Raspberry Pi lacks GICv3-ITS), and some apps need direct host access. For those, set `isolation: shared` and the app runs as a plain crun container. The console marks it clearly.
